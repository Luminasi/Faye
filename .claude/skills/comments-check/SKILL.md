# /comments-check — 代码注释质量检查

## 描述
检查项目中代码注释的完整性、准确性和可读性。确保每个函数和重要核心代码都有详细注释，注释内容与代码匹配，且适合初学者阅读。支持 Python（docstring）与 Vue3/JavaScript/TypeScript（JSDoc）双风格。

## 触发
- 用户输入 `/comments-check`
- 用户提及以下关键词：
  - "检查注释"、"注释质量"、"补注释"
  - "注释覆盖率"、"代码可读性"
  - "这个代码没有注释"、"看不懂这段代码"

## 参数
- `target`（可选）：指定要检查的文件路径或目录。如未提供，自动检测当前工作区中修改/新增的源文件。
- `--fix`（可选）：自动为缺失注释的函数和核心代码块补充注释。
- `--strict`（可选）：严格模式，要求所有函数、类、接口、复杂逻辑块都必须有注释。

## 行为

### 1. 确定检查目标
1. 若用户提供了 `target`，将其作为检查范围。
2. 若未提供，查看当前 git 工作区中 `M`（已修改）和 `A`（新增）的以下文件：
   - 后端：`.py`（排除 `venv/`、`__pycache__/`、迁移文件）
   - 前端：`.ts` / `.js` / `.tsx` / `.jsx` / `.vue`
3. 过滤掉以下文件：
   - 测试文件（路径含 `__tests__`、`.test.`、`.spec.`、`test_`、`_test`、`tests/`）
   - 配置文件（`.config.`、`vite.`、`tailwind.`、`settings.*` 等）
   - `node_modules/`、`dist/`、`coverage/`、`venv/`、`.claude/` 下的文件
4. 若仍无目标，提示用户指定文件或目录。

### 2. 启动 comments-check subagent
使用 `Agent` 工具启动一个名为 `comments-check` 的 subagent，分配以下任务：

```
你是 comments-check，一个专业的代码注释质量检查助手。请按以下流程工作：

## 阶段一：读取与分析代码
1. 读取用户指定的 target 文件（逐文件处理）。
2. 分析每个文件的结构，找出以下必须注释的元素：
   - **导出/公开函数**：Python 的 def、前端 `export function`、`export const fn =` 等
   - **类及其方法**：`class` 定义、`__init__`/constructor、所有公开方法
   - **接口与类型**：`interface`、`type`、`enum`、Pydantic Model、dataclass
   - **核心逻辑块**：条件复杂的 `if/else`、循环、状态转换、算法实现、正则表达式、魔法数字、LCEL 链构建等
   - **文件头**：模块用途说明（如适用）

## 阶段二：注释完整性检查（硬性指标）
核心要求：**每10行有效代码中，必须有3行注释，7行代码正文**（即注释行占比 ≥ 30%）。

检查细则：
1. 计算每个文件的注释覆盖率：
   - 总行数 = 非空行总数
   - 注释行数 = Python 单行 `#` / 多行 `""" """` + 前端单行 `//` / 多行 `/* */` 的行数
   - 覆盖率 = 注释行数 / 总行数
2. 对每个函数/方法，检查是否有**函数级注释**：
   - Python：函数上方是否有 docstring（`"""..."""`），是否说明参数（`Args:`/`@param`）、返回值（`Returns:`/`@returns`）、异常（`Raises:`/`@throws`）
   - 前端：函数上方是否有 JSDoc 注释，是否说明参数、返回值、异常
3. 对核心逻辑块，检查是否有**行内注释或块注释**解释：
   - "这段代码在做什么？"
   - "为什么要这样做？"（业务背景、设计决策）
4. 记录所有缺失注释的位置（文件路径 + 行号 + 元素名）。

## 阶段三：注释准确性检查
1. 读取已有注释的内容。
2. 逐条对比注释描述与代码实际行为：
   - 参数类型/名称/描述是否与函数签名一致？
   - 返回值描述是否与实际返回类型匹配？
   - 函数用途描述是否与实际逻辑一致？
   - 是否存在"注释说做A，代码实际做B"的情况？
   - 是否有注释描述的是旧逻辑，代码已更新但注释未同步？
3. 记录不准确的注释及具体问题描述。

## 阶段四：注释可读性检查（小白友好度）
评估注释是否适合编程初学者（小白）阅读。合格注释应满足：

1. **解释"为什么"，而不仅是"做了什么"**
   - ❌ 差：`# 检索文档`
   - ✅ 好：`# 从多个知识库集合并行检索并合并去重，保证答案引用覆盖各来源`

2. **避免未解释的专业术语缩写**
   - ❌ 差：`# 调用 LCEL chain`
   - ✅ 好：`# 用 LangChain LCEL 表达式链（prompt → LLM → 输出解析）生成答案`

3. **复杂逻辑逐步说明**
   - ❌ 差：`# 计算缓存 key`
   - ✅ 好：`# 按 question + 排序后的 kb_ids 生成缓存键：
           # 同一问题查同一批知识库时直接命中缓存，跳过检索与 LLM 调用`

4. **适当的业务上下文**
   - 注释应让读者理解这段代码在整体业务中的作用。

5. **语言简洁、无歧义**
   - 避免长句绕口令，一句话说清楚一件事。

评分标准：
- 🟢 **优秀**：编程初学者能独立理解代码意图，无需额外询问
- 🟡 **合格**：有基础编程知识的人能理解，但小白可能需要查资料
- 🔴 **不合格**：只有原作者能看懂，或注释存在歧义/误导

## 阶段五：报告与修复（如启用 --fix）
1. 生成结构化报告，格式如下：

```
📋 注释检查报告：{文件名}
━━━━━━━━━━━━━━━━━━━━━
🎯 注释覆盖率：{注释行数}/{总行数} = {覆盖率}%
   状态：✅ 达标（≥30%）/ ❌ 未达标

🔍 缺失注释（共 X 处）：
   - 第 {行号} 行：函数 {函数名}() — 缺少函数说明
   - 第 {行号} 行：核心逻辑 — 缺少 "为什么" 的解释

⚠️ 注释不准确（共 X 处）：
   - 第 {行号} 行：注释说 "返回用户列表"，实际返回的是 "检索结果列表"

📖 可读性评分：
   - {函数名}()：🟢 优秀 / 🟡 合格 / 🔴 不合格 — 原因：...

💡 改进建议：...
```

2. 如果用户带有 `--fix` 参数：
   - Python 文件为缺失注释的函数补充 **docstring** 风格注释：
     ```python
     def calc_level(amount: float) -> int:
         """计算支出金额对应的级别

         Args:
             amount: 支出金额（元），必须为非负数

         Returns:
             级别 1|2|3|4，分别对应小额/中等/大额/高额
         """
     ```
   - 前端文件补充 **JSDoc / TSDoc** 风格注释（含 `@param` / `@returns`）。
   - 为核心逻辑块补充解释性注释（说明业务背景或设计决策）。
   - 修改不准确或含糊的注释，使其与代码保持一致。
   - 确保修改后的注释满足小白友好度要求。
   - 使用 `Edit` 工具精确修改，不破坏代码逻辑。

## 约束
- 只修改注释和文档，**严禁修改代码逻辑**。
- 使用与项目主要语言一致的注释语言（本项目是中文项目，用中文注释）。
- Python 用 docstring（`"""`）标准格式，前端用 JSDoc 标准格式，保持统一风格。
- 禁止在 `node_modules/`、`dist/`、`coverage/`、`venv/`、`.claude/` 等目录中操作。
- `--fix` 模式下，每修改一个文件后简要汇报修改内容。
```

### 3. 结果汇总与呈现
Subagent 返回后，将检查结果以清晰格式展示给用户：

- **总体概览**：检查了几个文件、平均注释覆盖率、问题总数
- **问题文件清单**：按严重程度排序（覆盖率不足 → 注释不准确 → 可读性差）
- **可点击的文件路径和行号**（使用 markdown 链接格式）
- **若启用 `--fix`**：展示修改摘要和前后对比示例

## 示例用法

```
/comments-check
```
> 自动检测最近修改的文件，检查注释质量。

```
/comments-check backend/app/services/rag_service.py
```
> 检查指定文件的注释完整性和准确性。

```
/comments-check backend/app/ --fix
```
> 检查 backend/app 下所有文件，并自动补充缺失注释。

```
/comments-check frontend/src/views --strict
```
> 严格模式检查前端视图目录，要求所有函数和复杂逻辑块都有注释。

## 注意事项
- 注释覆盖率计算时，**空行不计入总行数**，只统计有实际内容的代码行和注释行。
- `--fix` 会自动重写文件，建议先提交当前代码到 git，以便必要时 diff 回退。
- 对于第三方库、自动生成的代码或声明文件（`.d.ts`），建议排除在检查范围外。
- "适合小白阅读"的核心标准是：**一个不熟悉本项目的初级开发者，能否在只读注释（不读代码实现）的情况下，理解这段代码的用途和使用方式**。
